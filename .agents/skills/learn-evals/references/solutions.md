# Hints and reference approaches

Read only the relevant lesson after an attempt or an explicit request. Do not pre-label the whole course.

1. Debrief each example only after the learner's attempt, or when they ask for the answer. In the first example, the tracker has no new issue: both lists are empty. The assistant confirmed a write that didn't happen. If the learner is stuck, first ask them to count the entries in each list; don't give the verdict with the hint. In `lying-tool`, the tool returns an issue object but the independently collected after-snapshot still has no issue. That return value doesn't establish that the issue was stored. Both are constructed failures, not captured model runs. For the follow-up with one saved issue, existence alone is insufficient: inspect whether its text preserves the report's feature, trigger, expected behavior, and actual behavior. Accept the learner's own wording; don't require memorized terminology.
2. “Creates an issue under notifications for a search bug” is observable and consequential. “Agent is bad” is neither an actionable category nor a criterion.
3. `gradeOutcome(output, {action:'create', feature:'issue-search'}).every(g => g.status === 'pass')` in `src/evals/grades.ts` is a reference structural grader. Have the learner explain the checks before using it. `missing-trigger` still passes: semantic preservation is a different criterion.
4. Empty exports hanging and large exports truncating are distinct failures despite similar titles. A closed duplicate creates a new issue under this explicitly fictional policy. Other products may choose a different policy; their evals should reflect it.
5. In `exercises/trajectory.ts`, walk events in order. Store each `tool_call` under its `id`; join a `tool_result` using its `toolCallId`. Skip results with `error`. A successful `search_issues` result must precede a successful `get_issue` result whose call has `arguments.id === expectedIssueId`; both must precede the `add_comment` call. A pending read does not count, even if its call came first. At the write call, require `arguments.issueId === expectedIssueId` as well as the completed search/read evidence. Separately require every criterion from `gradeOutcome(output, {action: "comment", issueId: expectedIssueId})` to pass. A correct argument cannot substitute for correct stored state, or vice versa. Accept alternate queries and candidate orders.
6. In `exercises/conversation.ts`, require nonempty `output.turns`. For each turn except the last, grade `{...output, ...turn}` against `{action: "clarify"}`, preserving the original `before` snapshot. Then grade the final output against the supplied expectation. All criteria must pass. Early issues, transient comments, and damaged-then-restored records must fail even if the ending looks correct. Question relevance remains a separate human check.
7. Debrief only after the learner records both calibration and validation labels, unless they explicitly request answers. The historical `judge-disagreement` capture used Nemotron 3 Super as a judge with rubric v1. It accepted an unsupported Redux cause/fix; this is not the current DeepSeek/v2 configuration. DeepSeek V4.1 Flash through DeepSeek agreed with reference labels on 3/3 calibration and 3/3 validation examples in the recorded smoke run. Those examples informed development, so this is not an untouched general-quality estimate. Don't make learners repair v1 when v2 already ships. Inspect disagreements or add new calibration cases. Exact evidence quotes are structurally verifiable; whether they justify a verdict still requires human judgment.
8. The synthetic demo has mixed successes. Keep every attempt; don't silently replace failures with retries. An at-least-one success is insufficient for unattended dependable work.
9. In `exercises/isolation.ts`, allocate `new Map<string, Tracker>()` inside the factory. The returned function looks up the trial ID, inserts `new Tracker(seed)` only when absent, and returns that tracker. A global map leaks between stores; a new tracker on every lookup loses same-trial state. The constructor clones the seed. This exercise does not implement the production lifecycle/expiry handling in `src/trials.ts`.
10. Make a bounded claim about the tested cases, separate task correctness from execution reliability, and record remaining semantic/human checks. A larger framework can add dataset storage, annotation and production monitoring without changing this reasoning.
